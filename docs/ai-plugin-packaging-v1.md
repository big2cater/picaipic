# PicAiPic AI Plugin Packaging v1

Date: 2026-06-30

This note defines the first local packaging rule for PicAiPic AI plugins. The
PicAiPic host installer and AI plugin packages are separate artifacts.

## Boundary

The Windows host package created by:

```powershell
.\build-exe.bat
```

contains the PicAiPic app body and host-bundled resources only. It must not
bundle `plugins\picai-*` directories into the app installer.

AI plugins are shipped as independent zip packages. A user or future plugin
manager registers an unpacked plugin directory with PicAiPic.

## Package Shape

A plugin zip contains one top-level directory named after the plugin id:

```text
picai-salut-color-0.1.0.zip
  picai-salut-color\
    picaipic.plugin.json
    picaipic.package.json
    README.md
    start.bat
    stop.bat
    install.bat
    backend\
      main.py
      requirements*.txt
      ...
```

`picaipic.package.json` is generated by the packaging script. It records the
plugin id, version, file list, SHA256 hashes, and packaging warnings.

## Manifest Validation

The packaging script validates the v1 manifest shape before creating a zip:

- required top-level fields: `schemaVersion`, `id`, `name`, `version`
- required compatibility field: `compatibility.pluginApi`
- required entry fields: `entry.kind`
- at least one declared capability
- required capability fields: `id`, `kind`, `name`, `version`, `inputs`,
  `outputs`, `invoke`
- duplicate capability ids are rejected
- duplicate menu contribution ids are rejected
- `contributes.menus[].capability` must reference an existing capability id

Package-time validation is intentionally local and lightweight. The host still
owns runtime validation, setup gates, smoke checks, and safe invocation.

## Host Install Flow

PicAiPic Settings > AI Plugins can install a generated plugin zip directly.
The host-side install command:

- accepts a `.zip` package selected by the user
- requires exactly one top-level directory
- requires the top-level directory name to match `picaipic.plugin.json.id`
- reads and parses both `picaipic.plugin.json` and `picaipic.package.json`
- requires `picaipic.package.json.packageKind` to be
  `picaipic-plugin-package`
- verifies package plugin id and version match the plugin manifest
- verifies each declared file's size and SHA256 hash
- rejects files that are not declared in `picaipic.package.json`
- rejects absolute paths or `..` path traversal entries
- unpacks the plugin into a temporary staging directory first
- validates the staged manifest before replacing the installed plugin directory
- registers the unpacked plugin path in the plugin registry
- returns package warnings so the UI can surface development-path or release
  readiness issues

The host install flow replaces an existing installed copy of the same plugin id
inside the user plugin directory. It does not remove separately registered
development directories, so duplicate plugin ids can still appear during local
development until that UX is tightened.

## Installed Storage Layout

Installed zip packages are code-only artifacts. The package directory is
replaceable, while runtime and plugin-owned data are persistent. The default
plugin store is `picaipic-local` next to the installed executable, so large
models and virtual environments do not silently fill the user's system profile
drive.

```text
<picai-install-dir>\picaipic-local\
  plugins\{plugin-id}\                  # installed package code
  plugin-data\{plugin-id}\              # config, logs, models, durable data
  plugin-runtimes\{plugin-id}\{envDir}\ # plugin-private runtime envs
  shared-runtimes\{runtime-id}\         # shared heavy runtime envs
  plugin-cache\{plugin-id}\             # disposable task cache
  plugin-outputs\{plugin-id}\           # durable task outputs
```

Settings > Plugins shows this root and lets the user choose another folder for
future installs and runtime setup. Existing plugin files are not moved
automatically. `PICAIPIC_PLUGIN_STORE_DIR` remains an advanced override and
wins over the saved Settings value when present.

Setup/start commands receive:

```text
PICAIPIC_PLUGIN_ROOT
PICAIPIC_PLUGIN_DATA_DIR
PICAIPIC_PLUGIN_CACHE_DIR
PICAIPIC_PLUGIN_LOG_DIR
PICAIPIC_PLUGIN_MODEL_DIR
PICAIPIC_PLUGIN_CONFIG_PATH
PICAIPIC_PLUGIN_RUNTIME_DIR
PICAIPIC_PLUGIN_ENV_DIR
PICAIPIC_PLUGIN_ENV_PATH
```

`PICAIPIC_PLUGIN_ENV_DIR` and `PICAIPIC_PLUGIN_ENV_PATH` point to the selected
absolute runtime directory. For `scope: "shared"` profiles this is under
`shared-runtimes\{runtime-id}`; for `scope: "plugin"` profiles this is under
`plugin-runtimes\{plugin-id}\{envDir}`; for external bindings, the plugin
receives the external Python/root values instead of creating a managed venv.
This keeps existing Windows scripts simple while preventing venvs from being
created inside the installed package code.

Plugins should write logs to `PICAIPIC_PLUGIN_LOG_DIR`, read/write local config
through `PICAIPIC_PLUGIN_CONFIG_PATH`, and look for bundled/downloaded model
files under `PICAIPIC_PLUGIN_MODEL_DIR`. Package-relative `logs`, `models`, and
`.venv*` directories are development conveniences, not release storage.

After a zip package is installed, the host creates the plugin storage
directories immediately. For a plugin id such as `banana2`, users can always
find its model drop folder here:

```text
<picai-install-dir>\picaipic-local\plugin-data\banana2\models\
```

If the manifest declares model paths, the host also creates the parent
directories and writes:

```text
<picai-install-dir>\picaipic-local\plugin-data\banana2\models\README.txt
```

The README lists each expected model file and whether it is required or
optional. For example, a manifest model path of
`models/foo/bar.safetensors` maps to:

```text
<picai-install-dir>\picaipic-local\plugin-data\banana2\models\foo\bar.safetensors
```

Plugin-private runtime environments live under:

```text
<picai-install-dir>\picaipic-local\plugin-runtimes\{plugin-id}\{envDir}\
```

Large AI runtimes should use shared runtime bindings instead of plugin-private
venvs. The sample plugins use shared IDs per runtime family, for example:

```json
{
  "scope": "shared",
  "kind": "python",
  "id": "python312-rocm72-torch291"
}
```

Shared IDs map to:

```text
<picai-install-dir>\picaipic-local\shared-runtimes\python312-rocm72-torch291\
<picai-install-dir>\picaipic-local\shared-runtimes\python312-cuda121-torch231\
<picai-install-dir>\picaipic-local\shared-runtimes\python312-cpu-torch231\
<picai-install-dir>\picaipic-local\shared-runtimes\python312-directml\
```

Compatible plugins reuse the matching shared environment instead of downloading
CUDA, ROCm, CPU torch, or DirectML dependencies repeatedly. Plugin-private
runtimes remain available only for incompatible dependencies, and the existing
runtime probe can still detect external Python/runtime bindings.

Current conflict policy:

- Implemented: the storage layout, setup environment injection, and install
  scripts support both shared runtimes and plugin-private runtimes.
- Implemented: a plugin author can choose `scope: "shared"` or
  `scope: "plugin"` in the manifest/profile.
- Not implemented yet: the host does not automatically compare requirements
  across plugins, detect version conflicts, or switch a shared profile to a
  plugin-private profile on the user's behalf.
- Future UI should show the selected scope, actual venv path, key installed
  package versions, and a clear "use private runtime" option when a shared
  environment is incompatible.

## Host Uninstall Flow

PicAiPic Settings > AI Plugins can uninstall a plugin installed from a package.
The host-side uninstall command:

- accepts a plugin id, not an arbitrary filesystem path
- resolves the target as `<plugin-store>\plugins\<plugin-id>`
- verifies the target is a directory inside the plugin store's `plugins`
  directory
- verifies the staged `picaipic.plugin.json` id matches the requested plugin id
- stops the host-managed plugin runtime best-effort before deleting files
- removes the installed plugin directory
- removes the installed path from the plugin registry
- clears profile, setup, runtime-probe, and task state for that plugin id
- keeps persistent `plugin-data`, `plugin-runtimes`, `shared-runtimes`, and
  `plugin-outputs` directories for now

Uninstall intentionally does not delete development plugin directories
registered from outside the user plugin directory, such as `plugins\picai-*` in
the source tree. Those paths can be unregistered from the Plugin Directories
section, but source/development files remain owned by the user.

A later uninstall UI should let the user choose whether to remove only the code
copy or also delete plugin data, models, logs, runtimes, and outputs.

This install/uninstall loop has been manually verified in the updated Windows
executable with the generated SA-LUT and NAFNet plugin zips.

## Included Files

Packages should include:

- `picaipic.plugin.json`
- `README.md`
- start/stop/install scripts declared by the manifest
- backend source files
- requirements files
- small static assets needed by the plugin adapter

Packages should not include:

- `logs\`
- `tmp\`
- `__pycache__\`
- `.pytest_cache\`, `.mypy_cache\`, `.ruff_cache\`
- `.venv*`, `venv`, or `env`
- `node_modules\`
- `.git\`
- `.env`, `.local.env`, `local.env`
- `.pyc`, `.pyo`, `.log`
- large model files unless a future package profile explicitly opts in

## Development Paths

Release packages must not contain hard-coded development-machine paths such as
`D:\ailab\...` in manifest, scripts, or backend source files. The package
script warns about absolute paths in release-scanned file types and
`-FailOnWarnings` turns those warnings into build failures.

Local development overrides belong in `.local.env`, copied from
`.local.env.example` when needed. That file is intentionally excluded from
plugin packages, so a developer can point a plugin at local Python, source, or
model paths without leaking those paths into the distributable zip.

Packaged plugins should default to shared runtimes for large compatible AI
runtime families, or plugin-private runtimes when dependencies are known to
conflict. Missing external source/model files should be reported through Probe,
Setup, or Smoke checks rather than encoded as machine-specific defaults in the
manifest.

Packaging warnings should also highlight obvious privacy-relevant network
behavior for human review, such as:

- packaged Python source that imports `requests`, `urllib`, or `socket`
- embedded `http://` or `https://` URLs in packaged text files
- manifests that declare runtime network access or selected-file upload
- setup downloads that do not declare explicit allowed domains

These warnings are advisory only. They do not provide runtime enforcement or a
security sandbox, but they help catch accidental privacy regressions before a
plugin zip is distributed. Runtime process confinement is enforced separately
by the host at spawn time (see `ai-plugin-contract-v1.md` → "Process
confinement"); it is transparent to the package and requires no packaging
change.

Use `-FailOnWarnings` when preparing stricter release candidates.

If PicAiPic still shows package warnings after a clean rebuild, check whether
the app is reading an older installed plugin copy under the user plugin
directory. Reinstall the newly generated zip from `dist\plugins\` so the host
loads the new `picaipic.package.json`.

## Signing

Release packages **must** be signed with an Ed25519 keypair; unsigned packages
are refused in release builds (developer mode `PICAIPIC_ALLOW_UNSIGNED_PLUGINS=1`
bypasses this for local iteration).

Generate a keypair once per author:

```bash
python scripts/sign_plugin.py generate-key
# prints: <base64 private key>  <base64 public key>
```

Sign at packaging time with `-SignKeyFile`:

```powershell
.\scripts\package_plugin.ps1 .\plugins\picai-salut-color -SignKeyFile .\my-key.txt
```

The script writes a `signature` object (`algorithm`, `publicKey`, `value`)
into `picaipic.package.json` covering the canonical JSON of that file
(compact, object keys sorted lexicographically, with the `signature` field
omitted). Both the Python signer (`json.dumps(sort_keys=True)`) and the
Rust verifier (`serde_json::Value`, whose default `Map` is a `BTreeMap`)
produce byte-identical output, so the signature is independent of struct
field declaration order and on-disk key order. At install time the host
verifies the signature, then prompts the user to trust the publisher (by
public key) on first install. Keep the private key out of the package and
out of source control.

## Script

Package one plugin:

```powershell
.\scripts\package_plugin.ps1 .\plugins\picai-salut-color
```

Package every plugin under `plugins\`:

```powershell
.\scripts\package_plugin.ps1 -All
```

One-click wrapper from the project root:

```powershell
.\package-plugins.bat
```

Strict mode:

```powershell
.\scripts\package_plugin.ps1 -All -FailOnWarnings
```

Default output:

```text
dist\plugins\
  picai-salut-color-0.1.0.zip
  picai-nafnet-restore-0.1.0.zip
```

## Rule For Future Work

Do not add plugin files to the PicAiPic host installer to solve plugin
distribution. Improve this independent plugin package format instead.
