> 2026-07-26 更新（黑洞主题实装收敛 · 照片区 WebGL 漩涡 · 扫描预览进度 · RAW 缩略图加速）：
>
> **分支：** `feat/black-hole-idle-theme`（未合 main；含前端主题 + 扫描/RAW 小修）
>
> **黑洞主题（产品现状）**
> - 设置主题菜单：**默认 / 复古 / CMYK / 黑洞**（无独立开关）。`themeId===3` 挂宇宙背景。
> - 宇宙层：`BlackHoleBackground` WebGL 解析近似（全分辨率、~30fps）+ Canvas2D 降级；Home 专用；`TitleBar` `z-50`；侧栏/顶栏玻璃半透明透出星空。
> - **引力触发：** 黑洞主题 + **主窗最大化** + **空闲 6 秒**（原 15s）+ 无 reduced-motion / 无 inputStack / 非库切换。
> - **照片扭曲（当前主路径）：** 不再用 CSS 卡片飞入作为主特效。最大化空闲后：冻结照片区可见缩略图 → `PhotoVortexLayer`（FragCoord 风格 UV 旋转透镜，`c = twist/(d-r)`，洞半径缓增，紫环）**仅扭曲照片区**；捕获后隐藏真实网格；交互立即退出。参考：`https://fragcoord.xyz/s/uq4op5g3`。
> - CSS `useGravityWarp` / v1.5 六层 warp **代码仍在**，但 GridView **不再驱动**（保留可回退）。
> - 强度：`settings.dynamicThemeIntensity`；黑洞下 appearance 锁定 + `data-theme=dark`。
> - 设计：`docs/guide/black-hole-idle-theme-design.md`（v1.4 基线，见文内「2026-07-26 现状」）；扭曲 spec 仍描述 CSS 层，**引力主路径以 PhotoVortex 为准**。
> - Runbook：`.mex/patterns/change-black-hole-theme.md`。
>
> **扫描「正在生成预览」卡死 / 很慢**
> - 现象：进度停在 `N-2`（如 216/218）很久。
> - 根因 1：缩略图**失败**时旧逻辑只加 `failed`、**不加 `processed`** → 阶段永远 `preparing_previews`。
> - 根因 2：RAW（`file_type=3`）走 heavy 低并发；且 `get_raw_thumbnail` 曾**先 demosaic**。
> - 已修：`process_thumbnail_task` **成功/失败都推进 processed**；缩略图超时（普通 45s / 重 120s）、embedding 超时 60s（`t_utils.rs`）。
> - 已修：RAW UI 缩略图 **优先机内嵌入 JPEG**，无可用嵌入图再 half_size demosaic（`t_libraw.rs`）。对 JPG+RW2 成对相册提速最明显。
> - Runbook：`.mex/patterns/fix-library-scan-selection.md`（文末 2026-07-26）。
>
> **验证**

> - 手测：黑洞 + 最大化 + 静止 6s → 照片区漩涡；动鼠标恢复网格。
> - 手测：导入含 RW2 相册，「生成预览」应更快且不应永久卡在 N-2。

## 多插件和环境隔离设计

PicAiPic 可以同时接入很多插件。每个插件应该独立：

- 独立插件目录。
- 独立 manifest。
- 独立启动脚本。
- 独立 Python 虚拟环境。
- 独立模型目录。
- 独立日志目录。
- 独立 HTTP 服务端口。

这样可以避免依赖冲突，例如一个插件需要 PyTorch CUDA，一个插件需要 ROCm，一个插件需要 DirectML 或旧版 numpy。

PicAiPic 本体不应该把所有 AI 依赖装进主程序，也不应该假设所有插件共享同一个 Python 环境。

## 显卡和运行后端分工

PicAiPic 本体负责平台级检测和协调：

- 操作系统。
- CPU 架构。
- GPU 厂商：NVIDIA / AMD / Intel / Apple。
- 候选后端：CUDA、ROCm、DirectML、OpenVINO、MPS、CPU。

插件负责判断自己的环境是否真实可用：

- 虚拟环境是否存在。
- Python 是否可运行。
- torch / onnxruntime / openvino 等依赖是否安装。
- 当前 torch 是否包含 CUDA 或 ROCm 支持。
- 模型权重是否存在、是否只是 Git LFS pointer。
- 自定义算子或本地模块能否导入。
- capability 是否能跑通最小测试。

当前 SA-LUT 插件已经能在 Windows AMD ROCm 环境下跑通。

## 插件环境安装策略思路

当前 SA-LUT 插件仍可通过 `.local.env` 复用本机已有环境：

```text
D:\ailab\20260610133133\backend\venv\Scripts\python.exe
```

后续插件安装不应该简单变成“本体替所有插件硬编码下载 CUDA/ROCm/DirectML”。更合理的方向是：

- 插件包声明自己是什么运行时，例如 `python-pytorch`、`python-onnxruntime`、`node`、`binary`。
- 插件包声明官方支持的 install profile，例如 CUDA、ROCm、DirectML、CPU。
- PicAiPic 本体检测本机 OS、CPU 架构、GPU 厂商和候选后端。
- PicAiPic 在插件声明范围内自动选择最合适的 profile。
- 安装环境优先复用 `shared-runtimes\<runtime-id>`，例如多个 PyTorch ROCm
  插件共用 `python312-rocm72-torch291`；如果插件作者/manifest 判断依赖会
  冲突，可以声明 `scope: "plugin"` 落到
  `plugin-runtimes\{id}\{envDir}`，不能污染主程序或系统 Python。宿主自动
  比较 requirements 并切换私有 runtime 仍是后续工作。
- 安装完成后必须跑 `/diagnostics` 和 smoke test，只有测试通过才标记可用。

关于 ROCm 和 CUDA 的特殊规则：

- ROCm 不是完整 CUDA 生态兼容，但在 PyTorch 层通常兼容 `torch.cuda` API。
- 很多纯 PyTorch 项目虽然代码写 `cuda`，在 ROCm 版 PyTorch 下也能运行。
- 因此对于 `python-pytorch` 插件，如果没有检测到 CUDA-only 依赖，本体可以从 CUDA API 兼容性推导出一个实验性 ROCm profile。
- 推导 ROCm profile 时，插件内部仍可能收到 `device = "cuda"`，因为 ROCm PyTorch 也是通过 `torch.cuda` 暴露设备。
- 但如果插件依赖 TensorRT、cupy-cuda、bitsandbytes CUDA wheel、自定义 `.cu` 算子、`nvcc`、`nvidia-smi` 等 NVIDIA-only 组件，则不能自动推导 ROCm。

推荐 manifest 方向：

```json
{
  "runtime": {
    "kind": "python-pytorch",
    "cudaApiCompatible": true
  },
  "install": {
    "kind": "python-pytorch",
    "requirements": "backend/requirements.txt",
    "smokeTest": {
      "command": "python backend/smoke_test.py"
    }
  },
  "installProfiles": [
    {
      "id": "windows-nvidia-cuda",
      "backend": "cuda",
      "supportLevel": "official"
    },
    {
      "id": "windows-amd-rocm",
      "backend": "rocm",
      "supportLevel": "derived",
      "derivedFrom": "cuda-api"
    },
    {
      "id": "windows-cpu",
      "backend": "cpu",
      "supportLevel": "fallback"
    }
  ]
}
```

安装选择建议：

1. 插件有官方 profile：优先使用官方 profile。
2. 插件是 PyTorch 且 `cudaApiCompatible: true`：AMD 机器可自动尝试派生 ROCm profile。
3. 派生 profile 必须安装到 shared runtime 或插件私有 venv，并且必须通过 smoke test。
4. 派生失败时自动回退到 DirectML 或 CPU，具体取决于插件声明和本机能力。
5. 未声明、无法推导、或检测到 CUDA-only 依赖时，不应自动下载 ROCm。

这一阶段已经从“环境探测 + profile 推导草案”推进到第一版 setup 执行：

- 增加宿主硬件探测命令，返回 OS、arch、GPU vendor、候选 backend。（已完成第一版，只读探测，不安装依赖）
- 扩展 manifest 类型，先支持 `runtime.kind`、`runtime.cudaApiCompatible`、`installProfiles`、`smokeTest`。（已完成第一版读取和展示）

## 未来插件制作器的环境转换思路

插件制作器以后不只做“把项目打包成插件”，还可以做“插件环境适配助手”。目标是让作者提供一个 CUDA / CPU / 普通 Python 项目后，制作器尽量分析项目并生成多个可安装 profile，例如 CUDA、ROCm、DirectML、CPU。

这个方向可行，但不能承诺所有 CUDA 插件都能自动转换。应该按风险分级：

1. 纯 PyTorch，代码只是使用 `torch.cuda`、`model.to("cuda")`、`torch.device("cuda")`：
   - 最容易转换。
   - ROCm 版 PyTorch 仍然通过 `torch.cuda` API 暴露设备。
   - 制作器主要替换安装依赖和 wheel 源，例如 CUDA 版 torch 改成 ROCm 版 torch。
   - 生成 `.venv-rocm`，跑 smoke test，通过后标记为可用。
2. PyTorch + 少量可替换依赖：
   - 可以半自动转换。
   - 制作器扫描 `requirements.txt`、`pyproject.toml`、import 语句和启动脚本。
   - 发现可替代包时给出建议，例如 CUDA wheel 替换为 ROCm/CPU/DirectML 版本。
   - 需要作者确认或手动修补。
3. CUDA-only 生态依赖：
   - 不能自动承诺转换。
   - 例如 TensorRT、`cupy-cuda*`、CUDA-only `bitsandbytes`、自定义 `.cu` 算子、`nvcc`、`nvidia-smi`、依赖 NVIDIA 驱动 API 的库。
   - 制作器可以给出阻塞报告和迁移建议，但不应直接生成“可用 ROCm”。

插件制作器可以分成几步：

- 项目导入：选择现有 Python/AI 项目目录。
- 静态扫描：读取依赖文件、Python import、启动命令、模型路径、CUDA-only 关键词。
- 运行时识别：判断是 `python-pytorch`、`python-onnxruntime`、`binary` 还是其他类型。
- 后端候选生成：根据扫描结果生成 CUDA、ROCm、DirectML、CPU 等 profile。
- 依赖转换：为不同 profile 生成独立 requirements 和安装脚本。
- 代码适配建议：把硬编码 `cuda` 的位置标出来，提示是否保持 `cuda` API 或改成 `auto` 设备选择。
- 自动验证：优先复用 `shared-runtimes` 中兼容的 CUDA/ROCm/CPU/DirectML
  runtime；如果 manifest/profile 选择 plugin-private，则为 profile 建插件
  私有 venv。后续要补 requirements/package-version 冲突检测，让 UI 能提示
  用户从 shared 切到 plugin-private。安装依赖后启动插件，跑 diagnostics 和
  smoke test。
- 打包输出：只有通过验证的 profile 标记为 `official` 或 `verified`，未通过的标记为 `experimental` 或 `blocked`。

对用户体验来说，插件制作器可以做成“转换报告”：

- 绿色：可以自动生成并验证，例如纯 PyTorch CUDA API 到 ROCm。
- 黄色：可以尝试派生，但需要 smoke test 或作者确认。
- 红色：发现 CUDA-only 依赖，不能自动转换。

这样以后别人做了一个 CUDA 插件，PicAiPic 插件制作器可以尝试把它转换成 AMD ROCm 版本；如果项目本身处在 PyTorch CUDA API 这一层，成功率会比较高。如果项目依赖 NVIDIA 专属生态，制作器就负责指出问题和给迁移路径，而不是假装已经兼容。

已完成的设计决策仍然成立：

PicAiPic 本体不应该为每个插件硬编码菜单按钮。正确做法是本体提供通用插件动作系统，插件通过 manifest 声明自己贡献哪些菜单项、工具栏按钮和能力入口。

第一版已经支持：

```json
"contributes": {
  "menus": [
    {
      "id": "picai-salut-color.image.color-transfer",
      "label": "SA-LUT 调色",
      "capability": "color-transfer",
      "contexts": ["image.selection.single"],
      "placements": ["image.contextMenu", "image.toolbar"],
      "icon": "palette",
      "order": 100
    }
  ]
}
```

字段含义：

- `id`：菜单项唯一 ID。
- `label`：显示给用户的名称。
- `capability`：点击后调用的插件能力 ID。
- `contexts`：适用上下文，例如 `image.selection.single`、`image.selection.multiple`、`album.selection`。
- `placements`：显示位置，例如 `image.contextMenu`、`image.toolbar`、`viewer.tools`。
- `icon`：图标名称，前端可映射到 lucide 图标。
- `order`：排序权重。

本体已经实现的通用逻辑：

1. 扫描所有已启用插件。
2. 读取 manifest 的 `contributes.menus`。
3. 根据当前上下文和 placement 过滤菜单项。
4. 渲染右键菜单或工具栏按钮。
5. 用户点击菜单后，根据 `capability` 找到对应插件能力。
6. 如果插件未启动，自动启动插件并等待 `/health`。
7. 打开通用参数面板，并使用插件声明的默认参数。
8. 调用 `invoke_ai_plugin_capability(pluginId, capabilityId, payload)`。
9. 成功后把插件输出文件导入图库，失败时显示 `/diagnostics` 和日志。

SA-LUT 插件目前已经在 `picaipic.plugin.json` 里加入了第一版 `contributes.menus` 示例：

```text
plugins/picai-salut-color/picaipic.plugin.json
```

目标流程：

1. 用户在 PicAiPic 图库中选中 source 图片。
2. 本体根据已启用插件的 `contributes.menus`，在右键菜单或工具面板动态显示“SA-LUT 调色”。
3. 选择 style 图片。
4. 选择设备偏好：`auto/cuda/rocm/cpu`。
5. 调用 SA-LUT 插件 `color-transfer`。
6. 插件输出结果图片路径。
7. PicAiPic 将结果导入图库。
8. 失败时显示插件 `/diagnostics` 和日志。

当前设置页里仍保留一个 SA-LUT 调试入口，但真正的图片工作流已经走通用插件动作执行器。
