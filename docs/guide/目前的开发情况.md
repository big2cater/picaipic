> 2026-07-07 更新：本轮完成了项目改名、签名加固、release 构建验证和 macOS 支持移除。

> **签名序列化加固**：Ed25519 包签名原来是脆弱的——Python 签名端用未排序
> 的 JSON key，Rust 验签端用 struct 字段顺序，两边靠字段顺序碰巧一致才验得过。
> 现在两端统一用字典序（Python `sort_keys=True`，Rust `serde_json::Value` 的
> BTreeMap），签名不再依赖字段声明顺序或磁盘 key 顺序。同时修了
> `Option::None` 序列化不一致（`signature`/`created_at` 加 `skip_serializing_if`）。
> 新增 4 个单元测试覆盖跨语言一致性、顺序无关性、篡改拒绝、真实 zip 端到端验签。
> 顺手修了 `sign_plugin.py generate-key` 的 bug（`PublicFormat.Raw` 应为
> `PrivateFormat.Raw`，原命令根本跑不起来）。

> 2026-07-04 更新：本轮落地了安全加固 Approach C（进程沙箱）的 v1 范围，
> 至此 A+B+C 三层安全模型已就位，v1 契约冻结的最后阻塞项进入验证阶段。
>
> **进程沙箱（deny-ACL 写限制）**：新增 `src-tauri/src/t_sandbox.rs` 模块。
> 插件进程 spawn 前，宿主对用户敏感目录（`%USERPROFILE%` 下的 Desktop、
> Documents、Pictures、Videos，以及环境变量 `PICAIPIC_SANDBOX_DENY_PATHS`
> 列出的额外路径）施加非递归 deny-write ACE（`icacls /deny <user>:(W) /L`）。
> 插件可写目录（`plugin-data`/`plugin-cache`/`plugin-outputs`/插件根/
> `plugin-runtimes`/`shared-runtimes`）被排除，不会误伤。`SandboxHandle`
> 的 `Drop` 调 `icacls /remove:d` 撤销 ACL，绑定 `RunningPlugin` 生命周期，
> 覆盖 stop / 崩溃检测 / 启动即退出 三条进程移除路径。GPU/CPU 访问完全保留
> ——`sandbox_gpu_spike.py` 已验证 deny-ACL 不破坏 ROCm/CUDA 驱动初始化。
> 开发逃逸开关：`PICAIPIC_DISABLE_PLUGIN_SANDBOX=1`。
>
> **源图预拷贝（input staging）**：`invoke_ai_plugin_capability_inner` 在
> 构造 payload 前，递归扫描 `inputs` JSON 的 `path` 字段，把落在插件可写区
> 之外的外部文件拷贝到 `plugin-cache/<id>/tasks/<taskId>/inputs/`，并改写
> payload 里的 path。插件读到的是 staging 副本，不需要原始磁盘位置的可读
> 权限。沙箱关闭时跳过预拷贝（零 IO）。
>
> **签名验证（Approach B，上一轮已落地）**：Ed25519 包签名 + 用户管理的
> 信任存储 + `TRUST_REQUIRED` 首装确认 + 开发模式 `PICAIPIC_ALLOW_UNSIGNED_PLUGINS=1`
> 放行未签名包。签名工具 `scripts/sign_plugin.py`，打包脚本支持 `-SignKeyFile`。
>
> **启动 token（Approach A，已落地）**：`PICAIPIC_PLUGIN_AUTH_TOKEN` bearer
> 校验，除 `/health` 外所有插件端点都要求 token。
>
> **spike hang 修复（前置）**：原 `sandbox_gpu_spike.py` 卡 300s 超时，根因是
> ROCm 7.2 + torch 在 Windows 上进程退出时 `amdhip64.dll` 的
> `DLL_PROCESS_DETACH` 死锁。spike v4 改用 `Popen` + 完成信号文件 + `terminate()`，
> 不再 `subprocess.run` 等进程退出。此问题和沙箱本身无关，但 spike 是 C 落地
> 的前置验证。
>
> 本轮验证：`cargo fmt --check`、`cargo check`、`pnpm --dir src-vite build`、
> `check_plugin_host.ps1` 全部通过；ACL apply/revoke 独立冒烟测试通过
> （deny 后写被拒、remove:d 后写恢复）。
>
> v1 沙箱范围外（future）：断网（WFP 或 restricted token）、macOS Seatbelt、
> Linux seccomp、严格 allow-list 写限制（restricted token 有丢 GPU 风险）、
> 大视频 inputs 零拷贝优化。

> 2026-07-10 更新：默认沙箱策略已调整为“源图预拷贝默认开启，Windows
> deny-ACL 写限制显式 opt-in”。原因是 deny-ACL 方案会临时修改当前 Windows

> `PICAIPIC_ENABLE_PLUGIN_ACL_SANDBOX=1`。开发逃逸开关
> `PICAIPIC_DISABLE_PLUGIN_SANDBOX=1` 仍会跳过 staging 和可选 ACL 处理。默认
> 插件启动还会 best-effort 清理旧版本/崩溃运行可能残留的 deny ACE。
>
> 本次验证：`cargo fmt --manifest-path src-tauri/Cargo.toml --check` 和

> 2026-07-03 更新：本轮完成了两项产品化工作。
>
> **运行时冲突检测**：宿主现在会把 probe 报告的已装包版本与插件 requirements
> 文件声明的版本说明符做完整比较。新增 `RequirementSpec`/`RuntimeConflict`
> 结构、`parse_requirements_file`（解析 requirements，跳过注释/选项/URL 行）、
> `parse_version`/`compare_versions`/`spec_satisfied`（手写最小 PEP 440 比较器，
> 支持 `==/!=/>=/<=/>/<` 和 `~=`，去掉 local version `+xxx`，未引入 semver 依赖）、
> `normalize_package_name`（`cv2`↔`opencv-python`、`skimage`↔`scikit-image` 等）、
> `detect_runtime_conflicts`（比较 probe 已装版本与 requirements 声明，产出
> `version_mismatch`/`missing`（阻断型）和 `unprobed`（信息型）三种冲突）。
> `PluginInstallProfileSummary` 新增 `runtimeConflicts` 字段，在
> `manifest_to_summary` 里对非 stale、passed 的 probe 自动计算。
> `ensure_runtime_probe_gate`（调用 capability 前的硬门）在有阻断型冲突时
> 硬阻断，返回"切 plugin-private runtime 或重跑 Setup"的可操作错误。Settings
> probe 卡片在 advice 列表上方显示冲突警告块：阻断型用黄色 `⚠`，`unprobed`
> 用灰色 `○`，并带"→ 切换到插件私有运行时"建议行。不自动切换 profile、不扩展
> probe 脚本去探测 NAFNet 的 `timm/skimage` 等私有包（记为 `unprobed` 不阻断）。
> 正常情况下两个插件 `==` pin 与正确 runtime 一致，`runtimeConflicts` 为空不阻断；
> 只有人为漂移（如 `pip install "numpy>=2"`）才触发。
>
> **卸载时选择**：卸载插件现在弹出 `UninstallModeDialog`（仿
> `FileConflictDialog`），提供两个选项卡片："仅代码"（普通样式，只删
> `plugins/<id>` 代码目录，与原行为一致）和"代码 + 数据和运行时"（破坏性
> `bg-error` 样式，额外删 `plugin-data/<id>`、`plugin-cache/<id>`、
> `plugin-outputs/<id>`、`plugin-runtimes/<id>`）。`shared-runtimes` 永远不删，
> 因为其他插件可能共享。`AiPluginUninstallResult` 新增 `mode` 和
> `removedExtraPaths` 字段；新增 `remove_existing_dir` 辅助函数（不触发
> `create_dir_all`，带 `is_path_inside` 安全检查）。`Settings.vue` 把原生
> `ask()` 二选一替换为应用内 `ModalDialog` 的 Promise 流程。i18n 文案
> `msgbox.uninstall.*` 中英文已补齐。

## 多插件和环境隔离设计

PicAiPic 可以同时接入很多插件。每个插件应该独立：

- 独立插件目录。
- 独立 manifest。
- 独立启动脚本。
- 独立 Python 虚拟环境。
- 独立模型目录。
- 独立日志目录。
- 独立 HTTP 服务端口。

这样可以避免依赖冲突，例如一个插件需要 PyTorch CUDA，一个插件需要 ROCm，一个插件需要 DirectML 或旧版 numpy。

PicAiPic 本体不应该把所有 AI 依赖装进主程序，也不应该假设所有插件共享同一个 Python 环境。

## 显卡和运行后端分工

PicAiPic 本体负责平台级检测和协调：

- 操作系统。
- CPU 架构。
- GPU 厂商：NVIDIA / AMD / Intel / Apple。
- 候选后端：CUDA、ROCm、DirectML、OpenVINO、MPS、CPU。

插件负责判断自己的环境是否真实可用：

- 虚拟环境是否存在。
- Python 是否可运行。
- torch / onnxruntime / openvino 等依赖是否安装。
- 当前 torch 是否包含 CUDA 或 ROCm 支持。
- 模型权重是否存在、是否只是 Git LFS pointer。
- 自定义算子或本地模块能否导入。
- capability 是否能跑通最小测试。

当前 SA-LUT 插件已经能在 Windows AMD ROCm 环境下跑通。

后续插件安装不应该简单变成“本体替所有插件硬编码下载 CUDA/ROCm/DirectML”。更合理的方向是：

- 插件包声明自己是什么运行时，例如 `python-pytorch`、`python-onnxruntime`、`node`、`binary`。
- 插件包声明官方支持的 install profile，例如 CUDA、ROCm、DirectML、CPU。
- PicAiPic 本体检测本机 OS、CPU 架构、GPU 厂商和候选后端。
- PicAiPic 在插件声明范围内自动选择最合适的 profile。
- 安装环境优先复用 `shared-runtimes\<runtime-id>`，例如多个 PyTorch ROCm
  插件共用 `python312-rocm72-torch291`；如果插件作者/manifest 判断依赖会
  冲突，可以声明 `scope: "plugin"` 落到
  `plugin-runtimes\{id}\{envDir}`，不能污染主程序或系统 Python。宿主自动
  比较 requirements 并切换私有 runtime 仍是后续工作。
- 安装完成后必须跑 `/diagnostics` 和 smoke test，只有测试通过才标记可用。

关于 ROCm 和 CUDA 的特殊规则：

- ROCm 不是完整 CUDA 生态兼容，但在 PyTorch 层通常兼容 `torch.cuda` API。
- 很多纯 PyTorch 项目虽然代码写 `cuda`，在 ROCm 版 PyTorch 下也能运行。
- 因此对于 `python-pytorch` 插件，如果没有检测到 CUDA-only 依赖，本体可以从 CUDA API 兼容性推导出一个实验性 ROCm profile。
- 推导 ROCm profile 时，插件内部仍可能收到 `device = "cuda"`，因为 ROCm PyTorch 也是通过 `torch.cuda` 暴露设备。
- 但如果插件依赖 TensorRT、cupy-cuda、bitsandbytes CUDA wheel、自定义 `.cu` 算子、`nvcc`、`nvidia-smi` 等 NVIDIA-only 组件，则不能自动推导 ROCm。

推荐 manifest 方向：

```json
{
  "runtime": {
    "kind": "python-pytorch",
    "cudaApiCompatible": true
  },
  "install": {
    "kind": "python-pytorch",
    "requirements": "backend/requirements.txt",
    "smokeTest": {
      "command": "python backend/smoke_test.py"
    }
  },
  "installProfiles": [
    {
      "id": "windows-nvidia-cuda",
      "backend": "cuda",
      "supportLevel": "official"
    },
    {
      "id": "windows-amd-rocm",
      "backend": "rocm",
      "supportLevel": "derived",
      "derivedFrom": "cuda-api"
    },
    {
      "id": "windows-cpu",
      "backend": "cpu",
      "supportLevel": "fallback"
    }
  ]
}
```

安装选择建议：

1. 插件有官方 profile：优先使用官方 profile。
2. 插件是 PyTorch 且 `cudaApiCompatible: true`：AMD 机器可自动尝试派生 ROCm profile。
3. 派生 profile 必须安装到 shared runtime 或插件私有 venv，并且必须通过 smoke test。
4. 派生失败时自动回退到 DirectML 或 CPU，具体取决于插件声明和本机能力。
5. 未声明、无法推导、或检测到 CUDA-only 依赖时，不应自动下载 ROCm。

## 未来插件制作器的环境转换思路

插件制作器以后不只做“把项目打包成插件”，还可以做“插件环境适配助手”。目标是让作者提供一个 CUDA / CPU / 普通 Python 项目后，制作器尽量分析项目并生成多个可安装 profile，例如 CUDA、ROCm、DirectML、CPU。

这个方向可行，但不能承诺所有 CUDA 插件都能自动转换。应该按风险分级：

1. 纯 PyTorch，代码只是使用 `torch.cuda`、`model.to("cuda")`、`torch.device("cuda")`：
   - 最容易转换。
   - ROCm 版 PyTorch 仍然通过 `torch.cuda` API 暴露设备。
   - 制作器主要替换安装依赖和 wheel 源，例如 CUDA 版 torch 改成 ROCm 版 torch。
   - 生成 `.venv-rocm`，跑 smoke test，通过后标记为可用。
2. PyTorch + 少量可替换依赖：
   - 可以半自动转换。
   - 制作器扫描 `requirements.txt`、`pyproject.toml`、import 语句和启动脚本。
   - 发现可替代包时给出建议，例如 CUDA wheel 替换为 ROCm/CPU/DirectML 版本。
   - 需要作者确认或手动修补。
3. CUDA-only 生态依赖：
   - 不能自动承诺转换。
   - 例如 TensorRT、`cupy-cuda*`、CUDA-only `bitsandbytes`、自定义 `.cu` 算子、`nvcc`、`nvidia-smi`、依赖 NVIDIA 驱动 API 的库。
   - 制作器可以给出阻塞报告和迁移建议，但不应直接生成“可用 ROCm”。

插件制作器可以分成几步：

- 项目导入：选择现有 Python/AI 项目目录。
- 静态扫描：读取依赖文件、Python import、启动命令、模型路径、CUDA-only 关键词。
- 运行时识别：判断是 `python-pytorch`、`python-onnxruntime`、`binary` 还是其他类型。
- 后端候选生成：根据扫描结果生成 CUDA、ROCm、DirectML、CPU 等 profile。
- 依赖转换：为不同 profile 生成独立 requirements 和安装脚本。
- 代码适配建议：把硬编码 `cuda` 的位置标出来，提示是否保持 `cuda` API 或改成 `auto` 设备选择。
- 自动验证：优先复用 `shared-runtimes` 中兼容的 CUDA/ROCm/CPU/DirectML
  runtime；如果 manifest/profile 选择 plugin-private，则为 profile 建插件
  私有 venv。后续要补 requirements/package-version 冲突检测，让 UI 能提示
  用户从 shared 切到 plugin-private。安装依赖后启动插件，跑 diagnostics 和
  smoke test。
- 打包输出：只有通过验证的 profile 标记为 `official` 或 `verified`，未通过的标记为 `experimental` 或 `blocked`。

对用户体验来说，插件制作器可以做成“转换报告”：

- 绿色：可以自动生成并验证，例如纯 PyTorch CUDA API 到 ROCm。
- 黄色：可以尝试派生，但需要 smoke test 或作者确认。
- 红色：发现 CUDA-only 依赖，不能自动转换。

这样以后别人做了一个 CUDA 插件，PicAiPic 插件制作器可以尝试把它转换成 AMD ROCm 版本；如果项目本身处在 PyTorch CUDA API 这一层，成功率会比较高。如果项目依赖 NVIDIA 专属生态，制作器就负责指出问题和给迁移路径，而不是假装已经兼容。

   - 旧实现使用 `cv2.imread(path)` / `cv2.imwrite(path)`。
   - 新实现使用 `numpy.fromfile + cv2.imdecode` 和 `cv2.imencode + tofile`。

   - `stop_ai_plugin` 会杀插件启动脚本的完整进程树。
   - Windows 下会按插件端口清理仍在监听的残留服务。
   - 主程序关闭和 Tauri `Exit` 事件都会调用 `stop_all()` 停止插件。
   - 设置页点击停止后会延迟刷新状态，避免 UI 仍显示运行中。

   - 宿主对 `startCommand`、`stopCommand`、`taskkill` 和 PowerShell 清理命令设置了 `CREATE_NO_WINDOW`。

   - 启动时优先尝试 manifest 的 `defaultPort`。

   - 宿主把真实端口注入 `PICAIPIC_PLUGIN_PORT`，并记录运行时 `baseUrl`。
   - `/status`、`/diagnostics` 和 capability invoke 都优先使用运行时 URL。
   - 设置页会显示实际运行 Runtime URL，方便调试多插件并发。
